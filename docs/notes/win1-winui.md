# WIN1: WinUI 3 backend (lane notes)

Status: slice 1 to 4 done as far as Linux can verify them, 2026-10-17. This builds on
`docs/notes/windows-gui-backend.md`, and Windows run steps are in `docs/notes/windows-setup.md`.

## What exists

| Piece | Where |
|---|---|

| Rust half: winmd -> JSON (`dump`), windows-bindgen wrapper (`bindgen`) | `tools/metadata/winui/winmd-tool/` (own `[workspace]`, built into `target/winmd-tool`) |

The slice has 8 kinds: `window`, `stack-panel`, `grid`, `text-block`, `button`, `check-box`,
`slider` and `text-box`. Across them it exposes:

- 48 props;
- 8 events: `click`, `text-changed`, `before-text-changing` (sync, `Cancel`), `key-down` (sync,
  `Handled`), `value-changed`, `checked`, `unchecked`, `closed` (the close rule);
- 3 slots: `content` on Window and on ContentControl, `children` on Panel;
- 4 child attributes: `row`, `column`, `row-span` and `column-span` on `grid`;
- 4 methods: `activate`, `close`, `select-all`, `select`.

That's 60 facts, each with a generated test.

## Decisions

- **Hosting: XAML Islands-style initialization, not `Application.Start`.**
  - The host loads the bundle, and so calls `create`, *before* `backend.run()`
    (`examples/counter/src/main.rs`: `Host::new` -> `load_bundle` -> `host.run()`).
  - `Application.Start` blocks, and it only lets us create XAML objects inside its callback.
  - So `WinUiBackend::new()` does `RoInitialize(STA)`, then the bootstrapper, then
    `DispatcherQueueController::CreateOnCurrentThread`.
  - It then composes an `Application` with our `IXamlMetadataProvider`, which delegates to
    `XamlControlsXamlMetaDataProvider`, and merges `XamlControlsResources`.
  - Last comes `WindowsXamlManager::InitializeForCurrentThread`.
  - `run()` is a `GetMessage` loop that calls `ContentPreTranslateMessage`.
  - This is the research recommendation (§5).
- **`window` is `Microsoft.UI.Xaml.Window`**, by the tag rule.
  - It's unverified that it can be created outside `Application.Start`; that's the top risk.
  - Fallback: our own HWND plus `DesktopWindowXamlSource`, with the kind still `window`.
- **Windows App SDK 2.5.1**, with WinUI 2.3.9, Foundation 2.3.12 and InteractiveExperiences 2.1.9.
  - Bootstrap constants come from `Microsoft.WindowsAppSDK.Runtime` 2.5.1
    `WindowsAppSDK-VersionInfo.json` **[verified]**: major.minor `0x00020005`, version tag `""`,
    min runtime `0x0002000500010000`.
  - The Runtime nupkg carries the runtime MSIX files.
- **The bootstrapper and `ContentPreTranslateMessage` are loaded with `LoadLibraryW`, not linked.**
  - They live in the framework package (`ContentPreTranslateMessage` is in
    `Microsoft.UI.Windowing.Core.dll`, per the import lib `Microsoft.UI.Dispatching.lib`
    **[verified]**).
  - A missing runtime must be a readable error, not a loader failure.
- **windows-rs 0.100 bindings are checked in**, generated by a member-level filter that
  `gen_backend.py` writes.
  - So builds need neither NuGet nor windows-bindgen.
  - Two bindgen 0.100 rough edges are handled in `winmd-tool bindgen`, mechanically, not from
    compile errors:
    - it adds `I*Factory`/`I*Statics` shells for every selected class and its bases;
    - it strips the `IntoIterator` impls that call an unselected `First()`.
  - Collections are driven through `windows_collections::IVector<T>` (the classes' default
    interface).
  - `Win32` functions must be named bare in the filter (`GetMessageW`): bindgen folds the
    Win32 namespaces into `Windows.Win32`.
  - The `Property.X`/`Event.X` filter sugar fails inside class filters, so raw accessor names
    are used.
- **windows-rs 0.100 event API.**
  - `Click(closure) -> EventRevoker`; dropping the revoker unsubscribes.
  - Handlers capture a `Sink` (handle + event id, two integers), never a COM reference. Our
    thread-local backend state routes the event.
  - Revokers that end inside their own handler go to a graveyard that is cleared on the next
    dispatcher turn.
- **No `Application` subclass for `OnLaunched`** (we never call `Start`). Composition is used
  only to answer `IXamlMetadataProvider` (`Application::compose`, `#[implement]`).
- **Ingestion is upstream facts only.**
  - `metadata/winui/*.json` hold winmd facts only, and `gen_backend.py` merges the overrides.
  - GTK merges them during ingestion instead. Override formats are per toolkit, and keeping the
    winmd output pure makes `ingest.py --check` a clean upstream-drift test.
- **The winmd reader is Rust** (`winmd-tool`, windows-metadata 0.100), driven from the Python
  `ingest.py`. Python only has raw ECMA tables (`dnfile`). The generator is Python, like GTK's
  and Qt's.
- **Naming.**
  - Tags are kebab of the class name, and members kebab of the native name; table tests enforce
    both.
  - Enums take the native or kebab name or the number, and come back as kebab names.
  - `Thickness` takes a number, the XAML string forms (`"8"`, `"h,v"`, `"l,t,r,b"`) or an
    insets record. It comes back as `"l,t,r,b"`.
  - `row-definitions` / `column-definitions` take the string form `"Auto, *, 2*, 40"` (hand
    converter `custom.rs`).
  - Child attributes are kebab too (`parent:row-span`). The ABI doc says camelCase; the user's
    naming rule wins.
- **Close rule.**
  - Every toplevel gets an always-on internal `Closed` handler.
  - While JS listens to `closed`: `Handled = true` and post.
  - Otherwise: report `SVL_GONE_CLOSED` for the window, then `SVL_GONE_PARENT` down the slot
    records.
  - `destroy` removes the entry first, so its own `Close()` is neither vetoed nor reported.
- **Sync events.** For `before-text-changing` and `key-down`, `call_sync` with `true` (from
  `e.preventDefault()`/`e.result`) sets the args' `Cancel`/`Handled`. Busy/failed replies leave
  the default.
- **Listen phases.** `listen_ex` with capture/after is refused with a reason. Routed-event
  phases (`AddHandler(..., handledEventsToo)`) are future work.
- **Styling.** The `style` member is left at the ABI default ("not supported"). The selector
  model (type, class, `Name` as id) and the setter table are prepared in
  `metadata/style/winui.yaml`.
- **The crate cfg-gates to its neutral part on Linux**: `table.rs`, `parse.rs` and
  `generated/names.rs`, with 12 unit tests. They run on Linux, so table and parser regressions
  show up in the normal gate. No `windows-*` crate is compiled off Windows.

## Shared-code changes (small, outside the lane's directories)

- `packages/renderer/src/index.js`:
  - `LABEL_KINDS` becomes `TEXT_PROPS`, with candidate props per tag. The first one the host
    resolves wins: GTK/Qt `button` -> `label`, WinUI `button` -> `content`, `text-block` ->
    `text`, `check-box` -> `content`.
  - `signalFor(type, tag)` keeps the DOM mapping (`click` -> `clicked`) unless only the unmapped
    name resolves, so WinUI keeps `click`.
  - Renderer tests: 44/44 pass.
- `tools/metadata/common/gen_bindings.py`:
  - WinUI toplevels come from the overrides (`window` opens with `activate`).
  - Candidate order is now `open` < `present` < others, so GTK keeps `present`. Before, `present`
    was sorted last, which would have picked GTK's own `activate` method.
  - `bindings.generated.js` regenerated.

## Open questions / next steps

- The first real Windows run: the checklist in `windows-setup.md` §5.
- `metadata/semantics/winui.json` is needed before the ST1 style checker and the compiler
  frontend (`@svelters/native-runtime`) can target WinUI. The example uses the stock renderer
  path for now.
- The verified-facts ledger: `src/generated/facts.json` has the fact -> test manifest.
  `tools/metadata/ledger.py` needs a `winui` toolkit that runs the tests on a Windows runner.
- More kinds: the generator is driven by the overrides, so adding a kind is a YAML file plus
  `regen.sh`. Any new value type (Brush, CornerRadius, FontWeight) needs a converter in
  `conv.rs`/`gen_backend.py`.
- Borrowed handles (objects the app didn't create) are not minted. `get_prop` of an object
  returns a handle only for our own objects.
- Win32 fallback: not built. The research probe (`win32_probe.c`) still stands as the
  always-runs-under-Wine smoke path if WinUI init proves fragile. The deciding facts will come
  from the first Windows run.
