## 1. GTK4 / GObject

### 1.1 GIR XML: what is represented and how

GIR (`/usr/share/gir-1.0/*.gir`, schema "GIR 1.2", namespaces `core`, `c`, `glib`) is
generated by `g-ir-scanner` from C sources plus gtk-doc/gi-docgen annotations, and
`g-ir-scanner` also runs a dumper binary against the real library, so GType-level facts
(hierarchy, property flags, signal flags, and since gobject-introspection ~1.80 property
default values) are derived from the registered types, not only from headers.

Element vocabulary counts in `Gtk-4.0.gir` (4.22.4): 269 `<class>`, 29 `<interface>`,
253 `<record>`, 112 `<enumeration>`, 20 `<bitfield>`, 456 `<callback>`, 1303 `<property>`,
348 `<glib:signal>`, 3348 `<method>`, 322 `<constructor>`, 782 `<function>`, 323 `<virtual-method>`.

| Concept | GIR representation |
|---|---|
| Class | `<class name parent glib:type-name glib:get-type glib:type-struct abstract final c:type>`; `parent` may be namespace-qualified (`GObject.InitiallyUnowned`) |
| Interfaces | `<implements name=.../>` on classes; `<interface>` with `<prerequisite>` |
| Constructor | `<constructor name c:identifier>` (e.g. `gtk_button_new_with_label`); return often declared as base type (`Gtk.Widget`), not the class itself |
| Property | `<property name readable(default 1) writable construct construct-only transfer-ownership getter setter default-value deprecated version>` + `<type>` or `<array>` |
| Property accessors | property has `getter`/`setter`; method has `glib:get-property`/`glib:set-property` (back-link) |
| Signal | `<glib:signal name when=first/last/cleanup action detailed no-recurse no-hooks>` with `<parameters>`/`<return-value>`; the emitter instance is implicit |
| Method | `<method>` with `<instance-parameter>` + `<parameters>` + `<return-value>`; `throws="1"` = trailing `GError**` |
| Virtual | `<virtual-method invoker=...>` |
| Enum / flags | `<enumeration>` / `<bitfield>` with `<member name value c:identifier glib:nick>`; `glib:type-name`, `glib:error-domain` |
| Nullability | `nullable="1"` (out/return), `allow-none="1"` (legacy in-arg), `optional="1"` (out pointer may be NULL) |
| Direction | `direction="in|out|inout"`, `caller-allocates="1"` |
| Ownership | `transfer-ownership="none|container|full"` on params, returns, properties; `<instance-parameter transfer-ownership>` |
| Arrays | `<array length="N" zero-terminated fixed-size c:type>` where `length` is the index of the length parameter; `<array name="GLib.PtrArray">` etc. |
| Containers | `<type name="GLib.List"><type name="Widget"/></type>` element types |
| Callbacks | `scope="call|async|notified|forever"`, `closure="i"` (user_data index), `destroy="i"` (GDestroyNotify index) |
| Async | `glib:async-func` / `glib:finish-func` / `glib:sync-func` links (newer g-i) |
| Availability | `version="4.10"`, `deprecated="1" deprecated-version`, `introspectable="0"`, `shadows` / `shadowed-by` |

Counts of annotations in `Gtk-4.0.gir`: transfer none 14549 / full 766 / container 24;
`nullable` 1275; `allow-none` 1059; `optional` 242; `caller-allocates` 110; `scope` 140;
`introspectable="0"` 807; `throws` 63; array `length` 62; `default-value` 984.

**Property defaults.** `default-value` is present on 984 of 1303 Gtk properties (Adw-1:
314 of 523). It is a *C literal string* (`"FALSE"`, `"NULL"`, `"GTK_ACCESSIBLE_ROLE_NONE"`).
Missing ones are mostly object/boxed/string types (51 `Widget`, 18 `Gio.ListModel`, 17
`utf8`, 16 `GType`, 11 `Gdk.RGBA`...). GIR does **not** carry numeric ranges
(min/max of `GParamSpecInt/Double`) nor `G_PARAM_EXPLICIT_NOTIFY`.

**Runtime introspection fills that gap.** `GObject.list_properties(gtype)` exposes each
`GParamSpec` with typed `get_default_value()`, `minimum`/`maximum`, flags (incl.
`EXPLICIT_NOTIFY`, `CONSTRUCT_ONLY`) and `owner_type`; `GObject.signal_query` gives signal
param GTypes, return GType and flags. It needs no display (no `gtk_init`). Proof:
`docs/notes/scripts/gobject_live_dump.py Button` -> 44 properties (incl. interface ones like
`GtkActionable:action-name`, `GtkAccessible:accessible-role`) and 16 signals;
e.g. `opacity: gdouble default 1.0 min 0.0 max 1.0 explicit_notify`. Limit: GTypes only
(no C type, no nullability/ownership, no method surface).

### 1.2 Parsers / readers

| Option | Notes | Verdict |
|---|---|---|
| Plain `xml.etree` / lxml over `.gir` | ~200 lines covers classes/props/signals/methods; must resolve `<include>` across namespaces yourself. Proof: `scripts/gir_dump.py Gtk-4.0 Button --chain` prints chain `Gtk.Button -> Gtk.Widget -> GObject.InitiallyUnowned -> GObject.Object`, 6 own props with types/defaults, `clicked`/`activate` (`when=first action`). | **Recommended primary** (stdlib-only Python, deterministic, easy to hash inputs) |
| `giscanner.girparser` + `giscanner.ast` (`/usr/lib/gobject-introspection/giscanner/`) | Gobject-introspection's own GIR reader -> typed AST (`ast.Class`, `ast.Property`, `ast.Signal`...). Not a stable public API, ships with the tool, path is not on `sys.path` by default. | Usable but couples us to g-i internals; nice for cross-checking |
| Rust `gir` tool (gtk-rs/gir) | Parses GIR into its library model, then reads per-crate `Gir.toml`; status per object `generate`/`manual`/`ignore`, per-function `manual = true`, `ignore = true`, nullability/`bypass_auto_rename` fixes; GIRs vendored and fixed with xmlstarlet scripts in [gtk-rs/gir-files](https://github.com/gtk-rs/gir-files). | Valuable as *curation evidence* (its overrides = known-bad annotations), not as our parser |
| Typelib via libgirepository (GIRepository-3.0, now in GLib >= 2.80) | Binary `.typelib`, same model minus docs/C types/default-values; this is what an invoker uses at runtime. | Runtime invocation, and cross-check that GIR == typelib for the pinned version |
| gi-docgen output | HTML + search `index.json` (names/kinds only) | Docs links only |

### 1.3 Child-container semantics (not in GIR as data)

GIR/typelib have **no** structured notion of "container" or named child slots.
GTK4 removed `GtkContainer` and child properties; layout attachment now lives on
`GtkLayoutChild` subclasses (`GridLayoutChild:row/column`, `ConstraintLayoutChild`) and
page objects (`NotebookPage`, `StackPage`, `AssistantPage`).

Upstream sources, in order of usefulness:

1. **GtkBuildable `<child type="...">` names** - documented only in prose sections
   `# GtkFoo as GtkBuildable` inside `<doc>` (32 such sections in Gtk-4.0.gir: ActionBar
   start/end/center, CenterBox start/center/end, HeaderBar start/end/title, Notebook tab /
   action-start/action-end, Overlay overlay, Window titlebar, Expander/Frame label,
   Dialog action, ...). The implementation is the `add_child` vfunc in C; not introspectable.
   There is no validation surface: verified that `GtkBox` given `<child type="bogus">`
   silently appends the child anyway (no error), so the accepted set cannot be probed.
   GtkPaned accepts `type="start"`/`"end"` but has *no* such doc paragraph (verified at runtime).
2. **Widget-typed writable properties** (`child`, `start-child`, `end-child`,
   `title-widget`, `titlebar`, `label-widget`, `center-widget`) = single named slots,
   machine-extractable. But false positives exist: `Window:default-widget`,
   `Window:focus-widget`, `Popover:default-widget`, `Stack:visible-child` are *references*,
   not ownership slots.
3. **Child-op methods** taking a `Gtk.Widget` (`append/prepend/insert_child_after/remove/
   reorder_child_after`, `pack_start/pack_end`, `attach`, `put/move`, `add_overlay`,
   `add_titled`, `insert_page`) = ordered/multi-slot containers, extractable by name pattern.

`scripts/gir_child_slots.py` runs heuristics 1-3 and finds 48 widget classes with child
surface, e.g.:

```text
Box         ops=[append, insert_child_after, prepend, remove, reorder_child_after]
Paned       props=[end-child, start-child]
HeaderBar   props=[title-widget] ops=[pack_end, pack_start, remove, set_title_widget] [buildable doc]
Window      props=[child, default-widget, focus-widget, titlebar] ...                  [buildable doc]
Notebook    ops=[insert_page, insert_page_menu, reorder_child, set_action_widget]      [buildable doc]
Grid        ops=[attach, attach_next_to, insert_next_to, remove]                       [buildable doc]
```

Verified under Xvfb (`GtkBuilder` with `<child type="start|end">` on GtkPaned and
`type="title"` on GtkHeaderBar resolves to `start-child`/`end-child`/`title-widget`).

**Conclusion:** child policy is generated as a *draft* from (2)+(3)+(1-prose) and then
**hand-annotated** in a checked-in override file (~50 GTK classes + Adw). It is small and
stable, so curation is cheap. libadwaita follows the same Buildable conventions
(`AdwHeaderBar`, `AdwToolbarView top/bottom`, `AdwNavigationSplitView sidebar/content`).

### 1.4 Dynamic invocation: how far can GObject/GI go without per-widget codegen?

Two layers, which should be evaluated separately.

**(a) Generic GObject property/signal path (no GI needed).** In Rust (current gtk-rs):
`ObjectExt::set_property_from_value(name, &Value)`, `property_value(name)`,
`ObjectExt::connect_closure(name, after, RustClosure)` / `connect_local`, `emit_by_name`.
Needs only a JS<->`glib::Value` converter keyed on GType fundamental: boolean, (u)int(64),
double/float, string, enum/flags (by nick or int), object (handle table), boxed (per-type
converter: `GdkRGBA`, `GStrv`, `GVariant`, `GtkRequisition`...), `GParam`.
Costs: `g_object_class_find_property` is a hash lookup; `g_signal_lookup` similar; both can
be cached per (GType, name) in a binding ID table. Per call we pay a `GValue` round trip;
that is cheap relative to the QuickJS boundary. Signal returns (`close-request`,
`query-tooltip`, `activate-link` return `gboolean`) require the JS handler to run
**synchronously** inside the emission; `RUN_LAST` vs `connect_after` matter for
"handled" semantics. Disconnect via `SignalHandlerId`; tie lifetime to the JS handle and
to `destroy`/dispose.

This covers construction (`g_object_new_with_properties` with construct-only props),
all props (44 for GtkButton) and signals. It does **not** cover ordinary methods.

**(b) GIRepository + libffi invoker (what PyGObject and gjs do).**
`gi_function_info_invoke()` (GIRepository-3.0; formerly `g_function_info_invoke`) takes
arrays of `GIArgument` in/out and calls through libffi; callbacks need
`gi_callable_info_create_closure` (libffi closure trampoline). All marshalling policy -
direction, length-argument pairing, ownership transfer, caller-allocated structs,
callback scope/lifetime, `GError` - is the caller's job (gjs `gi/arg-cache.cpp` +
`gi/function.cpp`, PyGObject `gi/pygi-invoke.c`/`pygi-argument.c`/`pygi-closure.c`, each
several thousand lines). Verified with PyGObject under Xvfb: `Widget.compute_bounds`
(caller-allocates `graphene_rect_t` out), `get_preferred_size` (two boxed outs),
`add_tick_callback` (scope=notified closure), `Box.append`, signal connect/emit/disconnect.

Classification of the 1733 constructors/methods/functions on the 104 `Gtk.Widget`
subclasses (`scripts/gir_callable_stats.py`):

```text
1613 (93%) no special feature (scalars, strings, enums, object/boxed pointers)
  60 out param               23 caller-allocates out     54 transfer-full in-arg
  17 callback scope=async    17 callback scope=notified   4 scope=call, 3 no scope
  12 zero-terminated/fixed arrays                         11 varargs
  14 introspectable="0"       1 shadowed-by
```

(All 269 Gtk classes: 3231 callables, 2833 plain.) What fails or needs bespoke work in a
generic invoker: varargs (never; use the `_v`/`_valist`-free alternatives or shadowed
variants), `introspectable="0"` (no typelib entry at all), callbacks with `scope="forever"`
or missing scope (lifetime unknown), `GList`/`GHashTable` transfer-container, caller-
allocated structs (need size from `GIStructInfo`), unions, `gpointer` user data,
non-boxed records, and **vfuncs** (overriding needs a subclass with a class_init; out of
scope for "use widgets", needed only for custom widget SDK).

**(c) Generated static bindings (gtk-rs style).** gtk4-rs already contains hand-reviewed
and generated wrappers for nearly all of this; calling them requires per-method Rust glue
(the 2021 svelters approach) and drives compile time. Plan SVR09/native-binding-linker
already chooses: **dev = (a)+(b) dynamic; release = direct `-sys` thunks only for methods
that survive JS DCE.** The findings support that: (a) covers props/signals/construction
for every widget with zero codegen, (b) covers ~93% of widget methods with a moderate
marshaller, and the remaining ~7% is explicit `Unsupported`/`CustomAdapter` data.
There is no maintained Rust crate that wraps `gi_function_info_invoke` with full
marshalling; budget for writing one (using `girepository-sys`-style FFI + the `libffi` crate
only for callbacks if GI's closure helper is insufficient).

### 1.5 GTK recommendation

1. **Primary extractor: Python (stdlib `xml.etree`) over the pinned `.gir` set**
   (GLib, GObject, Gio, Gdk, Gsk, Graphene, Pango, Gtk, optionally Adw). Emits the neutral
   JSON in section 4. Record GIR file hashes + gtk/g-i versions as provenance.
2. **Runtime enrichment pass: PyGObject** (`gobject_live_dump.py` style) over every
   `GObject` subclass to fill typed defaults, numeric ranges, `EXPLICIT_NOTIFY`,
   interface-contributed properties, and signal flags; and to **assert** GIR == runtime
   (fail the build if a property/signal disagrees). Needs no display.
3. **Typelib cross-check** (GIRepository-3.0) only to confirm every method we classify as
   `Introspected` is actually present in the typelib the dev runtime will load.
4. **Hand-annotated overrides** (YAML, checked in, keyed by canonical ID):
   child policy and slots (~50 GTK + Adw widgets), reference-vs-owned widget properties,
   attached/page properties (`StackPage:title`, `NotebookPage:tab-label`,
   `GridLayoutChild:row/column`), signals whose JS handler must return synchronously,
   callbacks with bad/missing `scope`, and the explicit `Unsupported` list with reasons.
   Seed the "bad annotation" list from gtk-rs `Gir.toml` + `gir-files/fix.sh`.
5. Do not use gtk-rs generated crates as the metadata source. They can be used in release
   thunks (call `gtk4::Button::set_label`) but the Plan's `-sys`/C thunk route is lighter.

**Every child-structure operation** in QtWidgets (`setCentralWidget`, `addWidget`,

`QPushButton -> QAbstractButton -> QWidget -> QObject`; own props `autoDefault`, `default`,
`flat` (bool, writable, designable, no notify); slot `showMenu()`; QAbstractButton signals
`pressed() released() clicked(bool) clicked() toggled(bool)` - note default arguments
produce *separate* metamethods (`clicked()` and `clicked(bool)`).

### 2.3 Other generators surveyed

- **Shiboken/PySide6**: the most complete curated model of QtWidgets; plan already adopts
  ApiExtractor (`plans/architecture/qt-shiboken.md`). Confirmed the typesystem carries the
  ownership facts we need (`<parent index="this" action="add"/>` on `addDockWidget` arg 2,
  `replace_child` on `setCentralWidget`/`setMenuBar`).
- **ritual / rust-qt**: libclang -> C wrapper + Rust; Qt5, unmaintained since ~2020; a
  cautionary example of generating everything (huge compile times).
- **cxx-qt (KDAB)**: Rust-defined QObjects + hand-written `cxx-qt-lib` bindings for core
  value types; no QtWidgets coverage, not a metadata source.
- **qmetaobject-rs**: Rust -> QML exposure; not relevant to widget bindings.
- **NodeGui**: hand-written C++ N-API wrappers per widget; shows the maintenance cost of
  manual wrapping (subset of widgets).
- **libclang / tree-sitter-cpp**: viable fallback for headers PySide does not cover
  (third-party widgets in SVR19), but loses all curation.

### 2.4 Qt recommendation

1. **Fast path now (no Shiboken build): qdoc index + live QMetaObject, in Python.**
   qdoc gives the full public function list, signatures, default args, access/virtual,
   property<->accessor linkage and enum values; PySide6 QMetaObject gives authoritative
   property/signal/slot/invokable and enum metadata for the exact Qt build. Join on class
   + signature. Enough for `.d.ts`, for classifying `Reflected` vs `GeneratedThunk`, and
   for generating thin C++ thunks for the ordinary methods we choose to support.
2. **Ownership/nullability overlay from the PySide typesystem XML** (parse with lxml:
   `parent`, `define-ownership`, `reference-count`, `replace_child`, removed functions).
   This is ~300 facts for QtWidgets and is exactly the knowledge raw headers lack.
3. **Long-term (SVR11): Shiboken ApiExtractor exporter** as the plan says, replacing (1)
   when it lands; keep (1) as a cross-check (qdoc vs ApiExtractor diff).
4. **Hand-annotated**: child slots (section 3), signal argument ownership and which
   QObject* returns are borrowed vs owned, event-handler virtuals we expose via event
   filters, and `Unsupported` reasons.

## 3. Semantics: children, slots, snippets, signals

### 3.1 Upstream sources that encode child structure

| Source | What it encodes | Machine-readable? |
|---|---|---|
| GtkBuildable `<child type="X">` | named child positions per widget (`start/end/title` on HeaderBar, `titlebar` on Window, `tab` on Notebook, `overlay` on Overlay, `start/end` on Paned) | prose in GIR `<doc>` only; behaviour in C `add_child` vfunc |
| GTK widget-typed properties / child-op methods | single slots (`child`, `start-child`) and ordered lists (`Box.append`) | yes (heuristic, needs curation; `scripts/gir_child_slots.py`) |
| GTK `GtkLayoutChild` / page objects | per-child attached props (`GridLayoutChild:row/column/row-span`, `StackPage:name/title/icon-name`, `NotebookPage:tab-label/reorderable`) | yes (GIR classes + `gtk_layout_manager_get_layout_child`, `gtk_stack_get_page`) |
| **uic** (`qtbase/src/tools/uic/cpp/cppwriteinitialization.cpp`, `WriteInitialization::acceptWidget`) and **QFormBuilder** (`qttools/src/designer/src/lib/uilib/abstractformbuilder.cpp`, `QAbstractFormBuilder::addItem`) | the canonical Qt mapping of a `.ui` child to a parent call, verified locally by running `/usr/lib/qt6/uic` on a sample `.ui`: child of QMainWindow -> `setCentralWidget` / `setMenuBar` / `addToolBar(area)` / `addDockWidget(area)` / `setStatusBar` depending on child class; QTabWidget -> `addTab(w, attribute title)`; QSplitter / QStackedWidget -> `addWidget`; QDockWidget / QScrollArea -> `setWidget`; QToolBox -> `addItem`; QMdiArea -> `addSubWindow`; QWizard -> `addPage`; layouts via `<layout>` + `<item row column rowspan colspan alignment>` | encoded in C++ switch; `.ui` *attributes* (`title`, `toolBarArea`, `dockWidgetArea`, `toolBarBreak`) are the attached-property vocabulary |
| Qt Designer container extension (`QDesignerContainerExtension`, `/usr/include/qt6/QtDesigner/container.h`) and `QDesignerCustomWidgetInterface::isContainer()/domXml()` | which widgets are page containers (stacked/tab/toolbox/MDI/wizard) with `addWidget/insertWidget/remove/currentIndex` contract; custom widget plugins declare container-ness | interface only; built-in list lives in Designer's widget database (`qttools/src/designer/src/lib/shared/widgetdatabase.cpp`, `widgets.table`) |
| PySide typesystem | ownership on insertion (`<parent index="this" action="add">`), slot replacement (`replace_child` template => old child released when set again), keep-alive (`reference-count`) | yes (XML) |
| Qt layouts vs widgets | `QLayout` is a QObject but not a QWidget: a widget has at most one layout (`setLayout`), children of a layout are re-parented to the layout's widget; nested layouts via `addLayout` | hand-annotate (model as a `layout` slot plus `LayoutManaged` policy) |

Nothing upstream gives a single "container kind" bit for either toolkit. **Child policy is
hand-annotated**, seeded by: GTK heuristics + Buildable prose; Qt uic mapping + Designer
container list + PySide ownership. Expected size: ~50 GTK, ~15 Adw, ~25 Qt entries.

### 3.2 Mapping Svelte constructs

- **Default children** (`{children}` / plain nested elements) -> the element kind's
  `default_slot` (Box: ordered `append`; Button/Window/ScrolledWindow: single `child`;
  QMainWindow: `central`; QSplitter: ordered `addWidget`; QWidget with layout: forwarded
  to its layout).
- **Named positions** -> named slots. Two viable Svelte surfaces; the IR supports both:
  (a) child attribute (mirrors `<child type>` and `.ui` attributes) e.g.
  `<HeaderBar><Button slot="start"/></HeaderBar>`; (b) snippet props,
  `<Paned>{#snippet start()}<Tree/>{/snippet}{#snippet end()}<View/>{/snippet}</Paned>`.
  Snippets are Svelte 5-idiomatic and type-checkable from generated `.d.ts`
  (`start?: Snippet`), so they should be the primary surface; attribute form is cheap to
  keep for multi-valued slots (`pack_start` lists).
- **Attached (per-child) properties** -> slot-scoped props on the child, e.g.
  `<Label grid:row={0} grid:column={1}/>`, `<Page tab:title="One"/>`,
  `<DockWidget dock:area="left"/>`, mapped to `GridLayoutChild` props / `StackPage` /
  `addTab(w, title)` / `addDockWidget(area, w)`. The IR stores them under the slot.
- **Ordering/moves** -> slot `ops`: `insert(index|after)`, `remove`, `reorder`; slots
  without reorder ops are recreated by remove+insert (or flagged as unsupported for keyed
  `{#each}`).
- **Model-driven** (GtkListView/QTreeView) are not child containers; out of scope here
  (SVR16).

### 3.3 Signal / slot semantics to capture

- **Return values**: GTK signals with `gboolean` return implement "handled/stop
  propagation" (`close-request`, `query-tooltip`, `activate-link`); accumulator semantics
  are not in GIR (`when` only). Qt signals almost never return values; vetoes happen in
  event virtuals (`closeEvent` + `QEvent::ignore()`), reachable without subclassing through
  `QObject::installEventFilter`. IR: `handler_result: none | bool_stop | value`, and
  `sync_required: true` when the JS handler must run inside emission.
- **Emission phase**: GTK `when=first|last|cleanup`, `connect` vs `connect_after`.
  Qt `Qt::ConnectionType` (direct/queued) is a connect-time choice; we always use direct
  on the GUI thread.
- **Blocking**: `g_signal_handler_block/unblock` and `QSignalBlocker`/`blockSignals`;
  needed to avoid feedback loops when the renderer sets a property that emits
  `notify::x`/`xChanged` (two-way `bind:`). IR: per property, `notify` signal + whether
  setter emits when unchanged (`EXPLICIT_NOTIFY` on GTK).
- **Lifetime**: GTK `SignalHandlerId` dies with the instance (`destroy`/dispose); Qt
  `QMetaObject::Connection` is auto-broken when sender or receiver context object dies -
  connect with a context QObject owned by the handle. JS handler references must be
  released on both paths. IR: `connection_semantics` already exists in the plan's Signal
  record; fill it with these.
- **Overloaded/defaulted signals**: Qt `clicked()` vs `clicked(bool)` are separate
  metamethods; the IR should collapse to one JS event with optional args.
- **Detailed signals**: GTK `notify::label` (`detailed=1`); map to `on:notify:label` or
  property-change events.

## 5. Recommended pipeline (summary)

```text
GTK:  .gir (Python/etree) ──┐
      PyGObject live pass ──┼─> merge+validate (Python) ─> canonical JSON ─> Rust codegen + .d.ts
      overrides/*.yaml  ────┘                                   (SVR07 tools)
Qt:   qdoc .index (etree) ──┐
      PySide6 QMetaObject ──┼─> merge+validate ─────────> canonical JSON
      PySide typesystem ────┤      (later: Shiboken ApiExtractor exporter replaces qdoc)
      overrides/*.yaml  ────┘
```

- Language: **Python** for extractors (stdlib + PyGObject/PySide6 already on target dev
  machines; trivially scriptable), emitting deterministic JSON; Rust consumes JSON in the
  `svelters-api-*` crates/codegen. Pin toolkit versions; store input hashes.
- Dynamic vs generated: GTK props/signals/construction fully dynamic; GTK methods via a
  GI invoker in dev (~93% of widget methods are "plain"), `-sys` thunks in release.
  Qt props/signals/slots dynamic via QMetaObject; constructors, child ops and ~42% of
  public functions need generated C++ thunks from day one.
- Hand-annotated: child policy/slots/attached props, reference-vs-owned widget props,
  sync/handled signal results, ownership exceptions, unsupported list, JS naming.
