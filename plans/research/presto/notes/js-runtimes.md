## 1. React Native New Architecture (Fabric, JSI, TurboModules, bridgeless)

### 1.1 What the old bridge got wrong
- Async, serialized bridge: "serializing function calls over the bridge quickly became a
  bottleneck, especially for frequent updates or large objects"; 60+ FPS hard to reach; JS/native
  falling out of sync produced "lists showing frames of empty space and visual UI jumps"; layout
  only on one thread, so urgent input couldn't be prioritised and layout couldn't be read
  synchronously; `onLayout` was async, causing "at least one incorrect frame" for tooltips. **[doc]**
  https://reactnative.dev/blog/2024/10/23/the-new-architecture-is-here (RN 0.76, 2024-10-23)
- Lesson **[inferred]**: the svelters "JS runs on the next frame" gap is exactly the bridge-era
  "one incorrect frame" problem. RN fixed it by making JS↔native calls synchronous (JSI), making
  layout readable synchronously, and letting high-priority events run the pipeline synchronously.

### 1.2 JSI / TurboModules / bridgeless
- JSI: C++ interface, "JavaScript and the native layer can now synchronously communicate"; return
  values can be references to native objects (host objects), no serialization; TurboModules are
  lazy-loaded and Codegen-typed. Bridgeless: globals bound directly in C++
  (`runtime.global().setProperty(...)`). **[doc]** same URL.

### 1.3 Fabric render pipeline
https://reactnative.dev/architecture/render-pipeline and
https://reactnative.dev/architecture/threading-model (current docs, read 2026-10-25) **[doc]**
- **Render** (JS thread, sync): React creates C++ Shadow Nodes synchronously through JSI, only
  for host components.
- **Commit** (background, async): Yoga layout, then "tree promotion"; text/TextInput measurement
  calls into the platform from Yoga.
- **Mount** (UI thread, sync): diff old vs new tree into atomic mutations (`createView`,
  `updateView`, `removeView`, `deleteView`), view flattening, then apply on the UI thread. "If the
  commit phase executes on background thread, the mounting phase is scheduled for the next 'tick'
  of UI thread. … if the commit phase executes on UI thread, mounting phase executes synchronously
  on the same thread."
- Shadow tree is **immutable**; updates clone the path to the root with structural sharing; one
  colour change yields a single `UpdateView`. Typical tree: 600–1000 nodes before flattening,
  ~200 after; desktop/iPad "may increase 10-fold".
- **C++ State** (e.g. ScrollView offset) is owned natively, "skip[s] the 'render phase' since
  React is not involved", "can originate and happen on any thread, including the main thread",
  and commits with optimistic concurrency: if another commit wins, "the C++ State commit will fail
  and the renderer will retry … until a commit succeeds".
- Threading model: UI thread is "the only thread that can manipulate host views". Scenarios:
  render on JS thread (normal); "When there is a high priority event on the UI Thread, the
  renderer is able to execute all the render pipeline synchronously on the UI thread"; low-priority
  (continuous) events interrupt and merge, rendering continues on JS thread; discrete events
  interrupt and complete synchronously on the UI thread.
- Concurrency: "React can interrupt a low-priority update to render an urgent one, such as those
  generated by user inputs"; transitions (`startTransition`) mark deferrable updates; automatic
  batching renders fewer intermediate states. **[doc]** 0.76 blog.
- `useLayoutEffect` + `getBoundingClientRect()` read layout synchronously during commit, so
  tooltips are positioned "before the user sees them". **[doc]** 0.76 blog.

### 1.4 Event categories, priorities, and synchronous UI-thread access (source)
- `RawEvent::Category` **[src]** `ReactCommon/react/renderer/core/RawEvent.h`:
  `ContinuousStart` (touchStart), `ContinuousEnd` (touchEnd), `Unspecified` ("priority … determined
  from other events in the queue"), `Discrete` (forced), `Continuous` (forced), `Idle`. Events can
  be `isUnique` (coalesced: only the latest is kept).
- Scheduler priorities and expiry timeouts **[src]** `runtimescheduler/SchedulerPriorityUtils.h`:
  Immediate 0 ms, UserBlocking 250 ms, Normal 5 s, Low 10 s, Idle 5 min. Selection: expired tasks
  first, then priority, then order (RFC 0744).
- React's own scheduler yields every **5 ms** (`frameYieldMs = 5`) **[src]**
  `react/packages/scheduler/src/SchedulerFeatureFlags.js`.
- `RuntimeScheduler_Modern::executeNowOnTheSameThread` **[src]**: "Grants access to the runtime
  synchronously on the caller's thread … expected to be used by dispatching a synchronous event via
  event emitter". It bumps `syncTaskRequests_` (which makes `getShouldYield()` return true, so the
  JS thread's running work yields), then calls
  `executeSynchronouslyOnSameThread_CAN_DEADLOCK(runtimeExecutor_, …)` — i.e. **the UI thread
  blocks until it owns the JS runtime**, runs one event-loop tick on the UI thread, and has to guard
  re-entry ("Without accounting for re-rentry, a deadlock will occur").
- Event-loop tick **[src]** (`runEventLoopTick`): take a `ScopedShadowTreeRevisionLock` (JS sees
  one consistent tree revision during the task), run task, `performMicrotaskCheckpoint`, report
  long tasks, then `updateRendering`: Event Timing entries → ResizeObserver callbacks (delivered to
  JS synchronously) → IntersectionObserver → drain `pendingRenderingUpdates_` (mounts).
- RFC 0744 "well-defined event loop" **[doc]**
  https://github.com/react-native-community/discussions-and-proposals/blob/main/proposals/0744-well-defined-event-loop.md :
  loop = select task → run → drain microtasks → update rendering; "each event loop iteration
  represents an atomic UI update"; commits are held until the "update rendering" step; synchronous
  events run exactly one loop iteration on the UI thread, "which avoids both unfinished UI states
  and unnecessary blocking"; layout effects get synchronous layout and paint waits for them, "the
  same way as React DOM".

**Takeaways [inferred]**: (a) the unit of atomicity is *one task + its microtasks*; (b) sync
UI-thread JS is used only for discrete/high-priority events, and the design needs a deadlock-safe
re-entry story when JS lives on another thread; (c) native-owned state (scroll) is committed by
native code without JS and must not be clobbered by stale JS commits.

## 2. Reanimated / react-native-worklets / Gesture Handler

- Runtimes **[doc]** https://docs.swmansion.com/react-native-worklets/docs/fundamentals/runtimeKinds :
  one RN runtime (JS thread); one **UI Runtime**, "mostly executed by the UI (main) thread",
  handles "responding to native touch events synchronously and computing animations"; any number of
  **Worker Runtimes** ("designed to execute worklets in a separate thread"). Worklet runtimes share
  no memory with each other or the RN runtime.
- Worklets: short functions marked `'worklet'`; a Babel plugin extracts the function and its
  captured closure into a serializable object copied to the target runtime; captured values are
  copies (reassignments don't propagate). "Bundle mode" gives worklets the whole bundle as
  precompiled bytecode instead of per-worklet string eval. **[doc/3rd]**
  https://docs.swmansion.com/react-native-worklets/docs/fundamentals/closures ,
  https://runtimes.margelo.com/docs/guides/vs-worklets
- `runOnUISync(worklet, …args)` runs a worklet synchronously on the UI runtime and returns a
  serializable result (Worklets 0.13). **[doc]**
  https://docs.swmansion.com/react-native-worklets/docs/threading/runOnUISync
- Shared values: synchronised between threads; "Reading shared values on the JS thread blocks that
  thread until the UI thread responds". **[doc]**
  https://docs.swmansion.com/react-native-reanimated/docs/guides/performance
- Gesture Handler: if callbacks are worklets, "all callbacks are executed on the UI thread",
  "handle gestures synchronously on the main thread"; `runOnJS: true` moves them to the JS thread.
  **[doc]** https://docs.swmansion.com/react-native-gesture-handler/docs/fundamentals/reanimated-interactions
- Performance guidance **[doc]** (performance guide above): animate ≤100 components on low-end
  Android, ≤500 on iOS; prefer non-layout props (transform, opacity) because layout props force a
  layout recalculation every frame.
- **The dual-write-path lesson** **[doc]**
  https://docs.swmansion.com/react-native-reanimated/docs/guides/feature-flags/ :
  `*_SYNCHRONOUSLY_UPDATE_UI_PROPS` applies non-layout styles directly to views, skipping
  `ShadowTree::commit`; "Changes applied via `synchronouslyUpdateViewOnUIThread` are not
  synchronized with changes applied by `ShadowTree::commit`", "may lead to minor inconsistencies …
  in a single animation frame". `DISABLE_COMMIT_PAUSING_MECHANISM` fixes sticky-header jitter but
  can cause "starvation of React commits". `FORCE_REACT_RENDER_FOR_SETTLED_ANIMATIONS`
  "periodically synchronizes animated style updates back to React".
  SWM deep dive (2025-03-11): Reanimated 4 routes layout *and* non-layout props through the
  ShadowTree "due to issues with view measurement and touch detection".
  https://swmansion.com/blog/how-react-native-reanimated-updates-the-styles-a-deep-dive-338ab22e9f21
- Margelo/Discord **[3rd, credible]** https://margelo.com/blog/margelo-discord-react-native-performance :
  Reanimated's commit hook re-cloned *every* node in the animated-props registry on every React
  commit ("we were cloning hundreds of shadow nodes"); fix = sync settled animations back to React
  and drop them from the registry (default since Reanimated 4.3.0), re-enable the sync fast path;
  Discord's Android jank-frame rate fell 26%.

**Takeaways [inferred]**: a native animation/gesture path that bypasses the authoritative tree is
fast but creates two sources of truth (hit-testing, measurement, stale JS commits overwriting
animated values). Design the retained tree so native-driven property values are *in* the tree
(one store, per-property owner), not a side channel.

- Web analogue: Animation Worklet ran scripted animations on the compositor thread ("off main
  thread (using compositor thread)") but never shipped beyond experiments **[doc]**
  https://www.chromium.org/teams/animations/animation-worklet ; the web instead shipped
  *declarative* scroll-driven animations (Chrome 115) that run "off the main thread"; JS scroll
  listeners are "impossible or very difficult" to keep in sync because scroll events arrive
  asynchronously **[doc]** https://developer.chrome.com/docs/css-ui/scroll-driven-animations

## 3. Lynx (ByteDance, open-sourced 2025-03)

- Dual-thread scripting **[doc]** https://lynxjs.org/blog/lynx-unlock-native-for-more.html :
  "statically-enforced division of user scripting into two distinct runtimes": a main-thread
  runtime (PrimJS) for launch and high-priority events, kept lightweight; a background runtime is
  the default for app code. Claims "2–4× reduction in launch times" for surfaces migrated from Web
  (internal, no benchmark published).
- Runtimes **[doc]** https://lynxjs.org/guide/scripting-runtime/index.md : main thread runs
  "main thread scripts, layout, and graphics rendering" (pixel pipeline), PrimJS, ES2019; background
  thread runs everything else (PrimJS on Android, JavaScriptCore on iOS), ES2015 + SWC transforms.
- Main-thread runtime **[doc]** https://lynxjs.org/guide/scripting-runtime/main-thread-runtime.md :
  PrimJS FFI wraps Lynx Elements as JS objects without a full object model (no getters/setters, only
  passable as parameters); only APIs "that do not affect rendering" are exposed beyond Element PAPI;
  main-thread scripts are precompiled to bytecode that "can be loaded about four times faster" than
  source.
- ReactLynx split **[doc]** https://lynxjs.org/react/thinking-in-reactlynx : main thread
  "responsible for rendering the initial screen and applying subsequent UI updates"; background runs
  "a complete React runtime, handling component lifecycles and other side effects". The compiler
  classifies code: event handlers, effects, ref callbacks, `'background only'` → background bundle
  only.
- Main Thread Script (MTS) **[doc]** https://lynxjs.org/react/main-thread-script.html :
  `'main thread'` directive; bind with `main-thread:bindscroll`/`main-thread:bindtap`; handler gets
  `MainThread.Element` and mutates it directly (`setStyleProperty`); state in `MainThreadRef`
  (`useMainThreadRef`); captured background values are passed by `JSON.stringify` and only refresh
  on re-render; captured variables are read-only; `runOnBackground`/`runOnMainThread` are async
  cross-thread calls. Event docs: main-thread handlers "avoid event delays caused by
  cross-threading" but "excessive event processing may cause the main thread to be busy".
- Instant First-Frame Rendering **[doc]** https://lynxjs.org/guide/interaction/ifr.md : if data
  is available at startup, the first screen renders synchronously on the main thread ("briefly
  blocking the main thread until the first frame is fully rendered"); fails if the bundle or main
  data load asynchronously. ReactLynx 0.123.0 added `markFirstScreenSyncReady()` to control the
  hand-over to the background thread. **[doc]** changelog via
  https://newreleases.io/project/github/lynx-family/lynx-stack/release/@lynx-js%2Freact@0.123.0
- Element PAPI **[doc]** https://lynxjs.org/api/engine/element-api/__createelement :
  `__CreateElement(tag, parentComponentUniqueID, info)` returns a ref-counted element; ~45 calls
  (`__AppendElement`, `__InsertElementBefore`, `__RemoveElement`, `__SetAttribute`,
  `__SetInlineStyles`, `__SetClasses`, `__AddEvent`, `__GetComputedStyleByKey`,
  `__FlushElementTree`, …). It is the same create/insert/set-prop shape as svelters' C ABI.
- Thread strategies: lynx-stack has PRs "support thread strategy all on ui" and "mark the
  multi-thread deprecated" **[3rd: PR titles only]**
  https://codspeed.io/lynx-family/lynx-stack/branches/PupilTong%3Ap%2Fhw%2Fdeprecate-all-on-ui —
  i.e. Lynx can also run *everything* on the UI thread; details not documented publicly.
- PrimJS **[doc]** https://github.com/lynx-family/primjs and
  https://github.com/lynx-family/primjs/blob/develop/docs/benchmark.md : QuickJS-based; template
  interpreter "leveraging stack caching and register optimizations"; a tracing GC instead of
  refcounting (enabled only on arm64 builds with pregenerated `embedded.S`); object model integrated
  with Lynx's. Octane v9 on M1 Max: QuickJS (commit 6e2e68) **2904** vs PrimJS **3735** (~+28%);
  per test from 0.94× (CodeLoad) to 2.16× (RayTrace).

**Takeaways [inferred]**: Lynx's answer to latency is *where* code runs, decided at compile time,
with a small privileged UI-thread runtime. The price is two runtimes, serialized captures and an
async boundary for everything else.

## 4. Valdi (Snap, open-sourced 2025-11, beta; 8 years in production)

Read from the repo docs at `ede1462` (cloned) **[doc]**:
- Runtime (`docs/docs/internals-runtime.md`): C++ runtime embeds "QuickJS on Android/Desktop,
  JavaScriptCore on iOS" plus Yoga. (Secondary articles claiming "no JS runtime" are wrong.)
- Threads: "Compiled TypeScript code runs in a JavaScript Virtual Machine using a single threaded
  event loop" (`advanced-worker-service.md`); "Logic which runs in the iOS/Android main thread is
  all C++ code" (`performance-optimization.md`); components "render asynchronously"
  (`native-collectionview.md`, with `waitUntilAllUpdatesCompleted` to wait). Native→JS calls
  "automatically asynchronously dispatch to the JS thread"; synchronous returns need a
  `createScopedJSRuntime` scope (`native-bindings.md`). Worker services run TS on a separate worker
  thread (default: one shared worker thread), promise-based, async in both directions.
- Commit protocol: after a render pass the TS renderer submits a `RenderRequest {treeId,
  descriptor: ArrayBuffer, values[]}`; binary commands with a 4-byte header (1 byte command, 3
  bytes element id): `CreateElement` 8 B, `DestroyElement` 4 B, `MoveElementToParent` 12 B,
  `SetAttributeInt` 12 B, `SetAttributeStyle` 12 B (pre-interned style), `SetAttributeAttachedValue`
  12 B (index into `values`). `Valdi::Value` is a 128-bit immutable, thread-safe, ref-counted value;
  strings interned (`StringBox`, pointer equality); attribute names interned as integers; `Style<>`
  objects interned lazily so the bridge passes one integer.
- Renderer (`internals-renderer.md`): incremental stack-based diff during render; components skip
  `onRender` when the view model is unchanged; slots re-render without the parent; removed
  attributes are not detected (set `undefined` explicitly).
- Interaction: gestures (tap, double tap, long press, drag, pinch, rotate) are recognised natively
  (UIGestureRecognizer on iOS; a C++ `TouchDispatcher` on Android/desktop Skia) and call
  marshalled JS callbacks; each gesture has `<gesture>Enabled` and an `on<Gesture>Predicate`
  (`core-touches.md`). Animations: `animate(options, () => mutations)` — mutations made inside are
  applied natively with a duration/curve/spring (CoreAnimation-style), no per-frame JS
  (`advanced-animations.md`). `<layout>` nodes are layout-only, no native view.
- Global view pool; only visible views inflated.

**Takeaways [inferred]**: the closest analogue to svelters (QuickJS, retained native tree, compiled
templates). Valdi keeps JS *off the UI thread entirely* and accepts async rendering; it removes JS
from the per-frame path by (1) native gesture recognisers, (2) declarative animations of the next
render's mutations, (3) cheap interned binary commits.

## 5. NativeScript, Hermes, Flutter (contrast)

- NativeScript: JS (V8/JSC) runs **on the UI thread** with direct, unserialized native API access;
  workers (Web Worker-like, message passing, no UI access) for heavy work. **[doc]**
  https://docs.nativescript.org/guide/multithreading . Andy Wingo (Igalia, 2023-04-24): "a
  NativeScript app is a native app which simply happens to call JavaScript on the main UI thread";
  jank risk from JS and GC on the UI thread, partly mitigated by V8 concurrent marking; but "There's
  no asynchrony between the application's logic and its main loop", so jank is easy to attribute.
  **[3rd, expert]** https://wingolog.org/archives/2023/04/24/structure-and-interpretation-of-nativescript
- Hermes **[doc]** https://reactnative.dev/blog/2021/10/26/toward-hermes-being-the-default :
  bytecode precompiled at build time; enabling Hermes "often cut a product's TTI … by nearly half";
  Hades GC "only pauses for 48ms at p99.9 on 64-bit devices (34x faster than GenGC!) and around 88ms
  at p99.9 on 32-bit devices (… single-threaded incremental GC)"; GenGC had "an average pause of
  200ms, or 1.4s at p99 … as long as 7 seconds" (Facebook for Android). Heap −30% from 32-bit
  pointer encoding.
- Static Hermes (RN EU 2023 deck, Tzvetan Mikov) **[doc]**
  https://speakerdeck.com/tmikov2023/static-hermes-react-native-eu-2023-announcement?slide=14 :
  sound-typed JS compiled ahead of time; nbody 5511 ms → 565 ms (~9.8×); native FFI call overhead
  "between 15x to 80x lower than JSI". Status as general-use release not confirmed.
- Flutter: platform channels are async message passing ("messages and responses are passed
  asynchronously … to ensure the user interface remains responsive") **[doc]**
  https://docs.flutter.dev/platform-integration/platform-channels . **Flutter 3.29 (2025-02) merged
  the UI and platform threads on Android/iOS** so Dart runs on the main thread, "allows making
  synchronous calls to and from the platform without the overhead of serialization and message
  passing" **[doc]** https://flutter.dev/blog/whats-new-in-flutter-3-29 ; macOS/Windows merged by
  default in 3.35, Linux in 3.39 **[doc]**
  https://docs.flutter.dev/release/breaking-changes/macos-windows-merged-threads.md ,
  https://docs.flutter.dev/release/breaking-changes/linux-merged-threads.md

**Takeaway [inferred]**: the industry trend 2024–2026 is *toward* synchronous, same-thread
interop with the UI (JSI sync events, Flutter thread merge, Lynx all-on-UI strategy), with
declarative/native mechanisms for the per-frame work.

  | JavaScriptCore (JIT) | 47255 | 53533 | 43752 |

  | QuickJS (bellard 2026-06-04) | 1201 | 1681 | 1107 |

  Reading **[inferred]**: QuickJS-NG is in Hermes-interpreter territory (0.5–1.1× Hermes depending on

- Bellard: "The complete life cycle of a runtime instance completes in less than 300
  microseconds"; hello world = 367 KiB x86 code; latest release 2026-06-04. **[doc]**
  https://bellard.org/quickjs/
- NG's perf changes over bellard: opcode fusion, polymorphic inline caching, allocation and parser
  improvements **[doc]** `docs/docs/diff.md` @ `7a23d8e`.

### 6.2 Cost of crossing the boundary (rquickjs 0.14)
- **[local]** svelters `docs/notes/egui-js-widgets.md` (measured on the WSL PC with rquickjs 0.14):
  - JS→native host fn call, one per op (`rect(x,y,w,h,rgba)`): **1.00–1.09 µs/op**, of which
    0.46–0.51 µs is QuickJS evaluating the argument expressions; the call itself adds ≈0.55 µs.
  - JS→native *method* (`painter.rect`): 1.12 µs/op. A JS→JS method call costs *more* than a
    JS→native call.
  - Batching into a `Float32Array` is *slower* in QuickJS (1.2–1.4 µs/op): typed-array stores are
    interpreted `put_array_el`s. JSON is 5–6× a native call per op.
  - **Rust→JS call: 0.14 µs**; passing an object built in Rust adds 2–3 µs per call → pass scalars.
  - Same op from Rust: 6 ns (~170× cheaper). Interrupt handler on/off: within noise (≤15%).
  - "Fit in 16 ms" ≈ 15k JS ops if the whole frame went to it; plan for a few thousand.
- rquickjs call path **[src]** `core/src/class/ffi.rs`, `core/src/result.rs`: a Rust closure is a
  JS class object; each call does `JS_GetOpaque` → vtable `call` → `catch_unwind` → `FromJs` per
  argument → result `IntoJs`. `Context::with` takes the runtime lock (a `RefCell` borrow without
  the `parallel` feature, a `std::sync::Mutex` with it) and calls `JS_UpdateStackTop` once per
  entry. String arguments need conversion/copies **[inferred]**, which is why Valdi and Lynx intern
  attribute names and styles.

### 6.3 GC behaviour
- Design **[doc]** `docs/docs/developer-guide/internals.md`: refcounting frees objects
  "automatically and deterministically"; "A separate cycle removal pass is done when the allocated
  memory becomes too large"; it uses only refcounts and object contents (no root registration).
- Trigger **[src]** `quickjs.c` `js_trigger_gc` (called from object allocation,
  `JS_NewObjectFromShape`): runs `JS_RunGC` when `malloc_size + size > malloc_gc_threshold`;
  initial threshold **256 KiB**; afterwards threshold = 1.5 × current heap. `JS_SetGCThreshold`
  overrides it.
- Algorithm **[src]** `JS_RunGC` = `gc_decref` (walk **every** object on `gc_obj_list`,
  decrement children's refcounts) → `gc_scan` (re-increment from survivors) → `gc_free_cycles`.
  It is non-incremental and non-concurrent: a pause proportional to the number of live GC objects
  in the runtime, at an allocation point the embedder doesn't choose **[inferred]**. No published
  pause-time measurements found (searched; none exist for NG). Separately, dropping the last ref to
  a big tree frees it synchronously (cascade) **[inferred from refcounting]**.
- PrimJS replaced refcounting with a tracing GC (arm64 only) for performance and leak safety
  **[doc]** (§3). Hermes went to a concurrent GC (Hades) because UI-thread GC pauses were 200 ms
  average / 1.4 s p99 **[doc]** (§5).

### 6.4 Runtimes, contexts, threads
- **[doc]** `docs/docs/developer-guide/intro.md`: "Several runtimes can exist at the same time but
  they cannot exchange objects. Inside a given runtime, no multi-threading is supported." Contexts
  (realms) in one runtime share objects and one heap/GC. quickjs-libc's `os.Worker` = a new
  `JSRuntime` on a new thread with message pipes; `JS_SetSharedArrayBufferFunctions` lets runtimes
  share SAB memory **[src]**.
- Memory per runtime/context: **no published figure found**; measure with
  `JS_ComputeMemoryUsage` before/after `JS_NewContext` **[doc: API exists]**.
- rquickjs: without `parallel`, `Runtime`/`Context` are `!Send` (Rc/RefCell); with `parallel`
  they are Send+Sync behind a mutex **[src]** `core/src/safe_ref.rs`, `core/src/context/base.rs`.
  One runtime per thread is the natural model.

### 6.5 Interrupts (budget enforcement)
- **[src]** `js_poll_interrupts` decrements a per-context counter (init **10000**) at back-edges
  (`OP_goto*`) and other polling sites (21 call sites), then calls the handler. **[inferred]** at
  ~10–50 ns per polled op that is a check every ~0.1–0.5 ms of busy JS.
- **[src]** When the handler returns non-zero, `JS_ThrowInterrupted` throws
  `InternalError("interrupted")` marked **uncatchable** (`JS_SetUncatchableError`). So the
  interrupt handler can only *abort* the running job; it cannot pause and resume it. QuickJS has
  no preemptive time-slicing; slicing must be cooperative (yield points, task splitting) or by
  moving work to another runtime/thread **[inferred]**.

### 6.6 Startup / bytecode
- **[local]** svelters `docs/notes/qjs-research.md`: 115-module unbundled graph (635 KiB source)
  from source ~95–120 ms; from recorded bytecode ~12–13 ms (322 KiB stripped); a tree-shaken
  229 KiB Vite bundle loads from bytecode in **3–4 ms**. Bytecode is tied to the exact NG build
  (BC_VERSION + config) and is trusted input only (also **[doc]** intro.md).
- Lynx: bytecode loads "about four times faster" than text **[doc]** (§3).

## 7. Fine-grained reactivity → retained native tree

### 7.1 Svelte 5 (5.57.2) scheduling — source
- `queue_micro_task` **[src]** `internal/client/dom/task.js`: Svelte's own queue, flushed by a
  single `queueMicrotask` callback.
- `Batch.ensure()` **[src]** `reactivity/batch.js`: the first `$state` write creates the current
  batch and queues `batch.flush()` as a microtask (unless already processing/flushing sync). The
  flush loops "until there are no more scheduled effects" (guard: >1000 iterations →
  `effect_update_depth_exceeded`), traverses dirty roots, then runs **render effects** (template
  updates → DOM ops) and then **user effects** (`$effect`), in that order, inside the same
  microtask. Async/pending work (`await` expressions) defers effects to a later batch.
- `flushSync(fn?)` **[src]**: sets `is_flushing_sync`, runs `fn`, then repeatedly `flush_tasks()`
  and `current_batch.flush()` until no batch remains — i.e. drain everything synchronously.
- Docs **[doc]** `documentation/docs/02-runes/04-$effect.md`: effects run "in a microtask after
  state changes. Re-runs are batched … and happen after any DOM updates have been applied";
  `$effect.pre` runs before DOM updates; `tick()` resolves once pending changes are applied
  (`06-runtime/03-lifecycle-hooks.md`); `mount`/`hydrate` don't run effects — call `flushSync()`
  (`06-runtime/04-imperative-component-api.md`).
- Event handling **[src]** `dom/elements/events.js`: delegated events (`delegate`,
  `handle_event_propagation`) — one root listener per event type; handlers run synchronously during
  dispatch, writes schedule the microtask flush.
- **Transitions/animations precompute keyframes** **[src]** `dom/elements/transitions.js`: for a
  `css` transition Svelte samples the user's `css(t, u)` at 60 fps
  (`n = Math.ceil(duration / (1000 / 60))`), builds a keyframe array, and calls
  `element.animate(keyframes, { duration, fill: 'forwards' })` (Web Animations API); only a `tick`
  transition runs JS every frame (via `loop`/`requestAnimationFrame`). `svelte/motion` (`Spring`,
  `Tween`) also runs per-frame JS through `raf` **[src]** `timing.js`, `loop.js`.
  **[inferred]**: a native `Element.animate()` in the backend makes every CSS-style Svelte
  transition run with zero per-frame JS.

### 7.2 Solid, Vue Vapor
- Solid universal renderer **[doc]** https://github.com/solidjs/solid/blob/main/packages/solid/universal/README.md :
  host implements `createElement`, `createTextNode`, `replaceText`, `insertNode(parent, node,
  anchor)`, `removeNode`, `setProperty`, `isTextNode`, `getParentNode`, `getFirstChild`,
  `getNextSibling` — the same shape as svelters' C ABI (note: it needs *read* navigation too).
- Solid 2.0 (RC, 2026) batches writes onto the microtask queue; `flush()` "synchronously
  process[es] the pending reactive queue", recommended "at the boundary of imperative integration
  code" and for focus management in event handlers. **[doc]**
  https://docs.solidjs.com/v2/reference/reactivity/flush
- Vue 3.6 Vapor (RC): no-VDOM compiled output, opt-in; project claims parity with Solid/Svelte 5
  in third-party benchmarks; alien-signals reactivity. **[doc, project claim]**
  https://newreleases.io/project/npm/vue/release/3.6.0-rc.1

**Convergence [inferred]**: Svelte 5, Solid 2, Vue all batch state writes into one microtask flush
and expose a `flushSync`/`flush` drain. So "one host call + drain microtasks" = one atomic batch of
DOM ops. That is the natural transaction boundary for svelters.

### 7.3 How browsers make event → pixel happen in one frame
- HTML event loop **[doc]** https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model :
  run the oldest task → "Perform a microtask checkpoint" → (when a rendering opportunity exists)
  update the rendering: resize steps, scroll steps, media queries, "update animations and send
  events" (Web Animations), fullscreen, **animation frame callbacks**, then a loop of "Recalculate
  styles and update layout" + ResizeObserver delivery, then paint. A microtask checkpoint also runs
  after each callback when the JS stack empties ("clean up after running script").
- Chrome aligns *continuous* input (wheel, touchmove, pointermove, mousemove) to the frame: since
  Chrome 60 they are dispatched "right before the requestAnimationFrame() callback" (−35% hit
  tests); intermediate points via `getCoalescedEvents()` (Chrome 58). **[doc]**
  https://developer.chrome.com/blog/aligning-input-events
- Scroll stays native unless a non-passive listener might `preventDefault`: Chrome 56 made root
  touch listeners passive by default; ~80% of cancelable root touch listeners were conceptually
  passive; slowest 1% of scrolls went from just over 400 ms to just over 250 ms touch-to-display;
  Chrome 73 did the same for wheel (">98%" of such listeners never call preventDefault).
  `touch-action` CSS declares intent instead. **[doc]**
  https://developer.chrome.com/blog/scrolling-intervention ,
  https://developer.chrome.com/blog/scrolling-intervention-2/
- Budgets **[doc]** RAIL https://web.dev/articles/rail : process input within 50 ms; produce
  each animation frame in ≤10 ms; idle work in ≤50 ms chunks; <100 ms feels immediate.
  INP https://web.dev/articles/inp : good ≤200 ms, poor >500 ms; latency = input delay +
  processing + presentation delay.

## 8. Design patterns for keeping JS off the critical path (synthesis)

| Pattern | Who | What the native side owns |
|---|---|---|
| Declarative pseudo-states | browsers (`:hover`, `:active`, `:focus-visible`) | state flags + style resolution, no JS |
| Native scroll + passive listeners | browsers, RN C++ State, Valdi `<scroll>` | scroll offset, momentum, sticky; JS notified after |
| Declarative scroll/gesture-driven animation | CSS scroll-driven animations; Valdi gestures with predicates | timelines bound to scroll/drag |
| Precomputed animations | Svelte `element.animate(keyframes)`, Valdi `animate()` | interpolation each frame |
| UI-thread mini-runtime | Lynx MTS, Reanimated worklets | small JS on UI thread, separate heap |
| Sync events on the UI thread | RN discrete events (`executeNowOnTheSameThread`) | JS runs inline in dispatch |
| Everything on the UI thread | NativeScript, Flutter ≥3.29, Lynx "all on UI" | nothing async; jank attributable |
| Async JS thread | Valdi, RN default | JS never blocks UI, UI lags JS by ≥1 frame |
| Worker runtimes | Valdi worker services, NativeScript workers, worklet worker runtimes, Lynx background | business logic off the UI thread |
| Priority + time-slicing | React scheduler (5 ms yield), RN RuntimeScheduler priorities | cooperative yielding, expiry |
| Binary, interned commits | Valdi RenderRequest; Lynx Element PAPI + flush | atomic op batch per render |

Trade-off of JS on a worker thread vs the UI thread **[inferred, from §1–§5]**:
- Worker: UI never waits on JS (GC, long handlers), but `preventDefault`, `getBoundingClientRect`,
  focus moves and "event → state → pixel same frame" all need a synchronous rendezvous. RN pays for
  it with a blocking acquire that "CAN_DEADLOCK", re-entry guards and revision locks; Lynx with a
  second runtime and serialized captures; Valdi gives it up (async render).
- UI thread: same-frame updates and sync APIs are trivial, and the browser model applies verbatim;
  risk is that JS time and GC pauses land on the frame. It works when (a) the toolkit does the
  per-frame interactions natively, (b) JS per frame is small (thousands of ops at ~1 µs), and
  (c) heavy logic lives in worker runtimes or Rust jobs.

## 9. Recommendations for svelters on the new framework

(Inferred design advice, based on the facts above.)

1. **Keep the Svelte runtime on the UI thread; run it inside event dispatch, not on the next frame.**
   - Frame order: collect OS input → native hit-test and native defaults (hover/active/focus
     flags, caret, IME, text editing, native scroll) → dispatch discrete events to JS one at a time,
     each followed by a microtask checkpoint (`JS_ExecutePendingJob` until empty, which runs
     Svelte's batch flush) → dispatch coalesced continuous events (one pointermove/wheel per frame,
     `getCoalescedEvents`-style history) → JS animation-frame callbacks → commit → style → layout
     → layout observers (bounded loop) → paint → present → idle work.
   - This removes the extra vsync. It is the HTML and RFC 0744 model. Flutter 3.29+, NativeScript
     and Lynx's all-on-UI mode run the same way.
2. **Transaction = one JS task plus its microtasks.** Buffer every create/insert/set_prop/listen op
   into a pending transaction. Apply it atomically at the checkpoint ("each event loop iteration
   represents an atomic UI update"). Never show a half-applied batch. Keep a tree revision so a
   commit from an older revision can't overwrite native-owned state (RN C++ State retries).
3. **One property, one owner.** Native-driven values (scroll offset, animation progress, drag
   position, hover/active, text selection) live in the retained tree as native-owned state. JS reads
   them and receives change events, and only writes them through explicit commands. Reanimated's
   flags and the Discord regression show what a side channel costs.
4. **The toolkit must do these natively, with zero JS per frame:**
   - CSS pseudo-states (`:hover`, `:active`, `:focus`, `:focus-visible`, `:disabled`) and CSS
     transitions on them;
   - scrolling (kinetic, wheel, scrollbars, sticky), with listeners passive by default and a
     `touch-action`-like property to opt out;
   - `Element.animate()`/WAAPI keyframes (Svelte transitions already emit them), plus native
     springs/tweens to replace `svelte/motion`'s raf loop;
   - text input, caret, IME and selection;
   - drag via declared constraints (axis, bounds, snap, drop targets), splitters, docking, virtual
     lists (row recycling like Valdi's view pool), tooltips and popover positioning.
   - JS gets semantic events (`change`, `dragend`, `drop`), not per-pixel ones, unless it opts in.
5. **Sync calls (preventDefault, layout reads) are cheap because JS is on the UI thread.**
   - Mark listeners `passive` by default (Chrome's data: >80–98% never call preventDefault).
   - Non-passive listeners on a scroll/drag path make that gesture wait for JS. Report it in the
     inspector.
   - `getBoundingClientRect` while the tree is dirty forces a synchronous layout. Allow it and
     count forced layouts per frame, as browsers do.
   - Add a post-layout, pre-paint observer phase (ResizeObserver/`useLayoutEffect` equivalent) so
     tooltips land correctly in the first frame.
6. **Budgets and preemption.**
   - QuickJS can't pause and resume a job. Its interrupt throws an uncatchable error, so use it
     only as a watchdog: abort and report after, say, 250 ms (RN's UserBlocking expiry) or a
     configured limit.
   - Give per-frame JS a soft deadline (e.g. 4–6 ms at 120 Hz). Discrete events always run.
     Continuous events, rAF callbacks, timers and idle tasks go in a priority queue with expiry
     (Immediate 0 / UserBlocking 250 ms / Normal 5 s / Idle), and the rest spills to the next frame.
   - Report long tasks over 50 ms (RAIL/RN `reportLongTasks`) with a JS stack.
   - Provide a `scheduler.yield()`/`isInputPending()` API for cooperative slicing.
7. **GC policy.**
   - Default QuickJS GC runs a full stop-the-world cycle collection at an allocation once the heap
     grows past 1.5× its size after the last GC (initial threshold 256 KiB), possibly mid-interaction.
   - Raise the threshold and call `JS_RunGC` in idle time, after present when no input is pending.
   - Bound heap size per runtime so the cycle pass stays short.
   - Measure GC pause against heap size on our build before choosing numbers. Nothing is published.
8. **Threads.**
   - Run one UI runtime (all Svelte panels as contexts or one context) on the UI thread.
   - Run worker runtimes (one `JSRuntime` per thread; rquickjs non-`parallel`) for extension
     business logic, parsers and anything over a few ms. Use message passing or SAB, Valdi-style
     promise APIs.
   - Kernel work stays in Rust jobs.
   - Keep the op ABI thread-agnostic (op buffers carry ids, not pointers) so a panel can later move
     to a Lynx-style background runtime if needed.
9. **Op encoding.**
   - Per the local measurements, use one native host call per op with scalar args. Typed-array
     batching and JSON are slower in QuickJS.
   - Intern property names and style objects to integer ids, as Valdi and Lynx do.
   - Pass strings once and keep Rust→JS calls scalar (0.14 µs vs 2–3 µs with objects).
   - Expect ~1 µs/op, so a few thousand ops per frame of change is fine. Per-frame animation must
     not go through JS.
10. **Startup.** Ship a tree-shaken bundle as NG bytecode built by the same NG build (3–4 ms load
    measured), and keep a per-module bytecode cache in dev. Render the first frame synchronously
    (Lynx IFR) so panels never show an empty frame.
11. **Optional, later:** a compile-time "UI-thread handler" subset (Lynx `'main thread'`,
    worklets) is unnecessary while JS already runs on the UI thread. An AOT path (svelters E-W2,
    Static Hermes-like) is the lever for hot JS paint code (~170× in the local measurements).
