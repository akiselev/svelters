# Custom and third-party native widgets: design proposal

Status: proposal (2026-10-17). Research and probes are in `docs/notes/custom-widgets-research.md`, and the probe scripts are `docs/notes/scripts/cw_adw_gir.py`, `cw_moc_json.py` and `cw_qt_reflect.py`. Nothing here is implemented.

## Summary

- **A widget pack** is one installable unit per toolkit library:
  - metadata (ingested kinds, overrides, a verified-facts ledger, a style-table fragment);
  - generated typings, docs IR, gallery and verification tests;
  - an optional native crate.
- **It ships as an npm package**, plus a crate when it has native code. First-party packs live in-repo under `packs/<name>/`.
- **Packs plug into the backend, not the host.**
  - The core backend keeps owning handles, lifetimes and the toolkit loop.
  - A pack contributes kinds in its own id range.
  - Each member call is routed to the pack or to the core by the id's pack bits.
- **There are two kinds of pack:**
  - A **data pack** has no compiled code. The backend's reflective engine drives it: GObject + GIRepository, ObjC runtime, the WinUI `IXamlMetadataProvider`, or Qt designer plugins + QMetaObject. It works in a prebuilt runner with no build.
  - A **code pack** has generated or hand-written native glue behind a small C vtable (`svl_pack`). It is statically linked through the app's leaf crate, or dlopen'd later on desktop. Qt libraries such as ADS are code packs.
- **ABI impact: one additive `svl_backend` member** (`add_pack`, ABI v2.5) and a new header `svelters_pack.h` for the backend↔pack interface. The host↔backend semantics don't change. Ids gain a pack field in bits 22..27.
- **Pilot: libadwaita.** It is a GIR data pack, exercises every host-visible part (prefix, id ranges, version gating, init hook, style takeover, non-widget kinds, docs/typings/gallery) and needs no native code. After it:
  1. an app-authored GTK widget;
  2. the Qt reflective path with an app-authored `Q_OBJECT` widget;
  3. ADS as the first code pack;
  4. WinUI and Apple packs once those backends exist.

## 1. Cases and what each needs

| Case | Metadata source | Create by name without our code? | Members without our code? | Pack kind |
| --- | --- | --- | --- | --- |
| libadwaita | `Adw-1.gir` (90 classes, 62 widgets, `since` on all) | yes: the typelib loads `libadwaita-1.so`; `g_type_from_name` | props/signals via GObject, methods via GIRepository (X1) | data |
| App GTK widget in Vala/C | GIR + typelib from `valac --gir`/`g-ir-scanner` | yes | yes | data |
| App GTK widget in Rust | runtime GObject introspection (props, signals); no GIR | once registered (`T::static_type()`) | props/signals yes; methods only if exported to GI (usually not) | code (one registration line) + runtime-derived metadata |
| ADS (Qt) | `moc --output-json` (49 signals, 72 slots, 17 props) + libclang (591 public methods) + its PyQt `.sip` (`/Transfer/` ownership) | no (no designer plugin, no `Q_INVOKABLE` ctors) | signals/slots via QMetaObject; container API (`addDockWidget`, `saveState`) not | code |
| App Qt `Q_OBJECT` widget | moc JSON + libclang | no: needs a factory | `Q_PROPERTY`/signals/slots via QMetaObject | code (factory) or generated |
| Qt lib with a designer plugin | moc JSON | yes, via `QUiLoader::createWidget` | via QMetaObject | data |
| WinUI C++/WinRT control lib (Win2D) | its `.winmd` | yes: `DllGetActivationFactory` from the pack's dll + its `IXamlMetadataProvider` | props yes (`IXamlMember`); events need the universal delegate or generated `add_X` | data once WIN1's dynamic events exist; code until then |
| Windows Community Toolkit | none usable natively: C#, not a WinRT component | only through a C#/WinRT-authored wrapper hosting .NET | as above, through the wrapper | code (+ .NET runtime) |
| ObjC framework / `@objc` Swift view | headers or `Module-Swift.h` through the MAC1 libclang pass | yes (`objc_getClass`/`NSClassFromString`) | KVC, generic target/delegate | data (macOS dynamic frameworks); always linked on iOS |
| Swift-only API, SwiftUI | `.swiftinterface` (only to see what is missing) | no | no | code: `@objc` shim / hosting view |
| Svelte composite | its TS props | n/a | n/a | an ordinary npm package of `.svelte` files; no native layer |

The reflective path that GTK, ObjC and WinUI already plan for dev builds also covers third-party libraries on those toolkits. Qt is the outlier: it has no reflective dev path today, and C++ libraries rarely expose enough through QMetaObject.

## 2. The pack

### 2.1 Layout

```text
packs/adw/                         (first-party in-repo; third-party packs use the same layout in their own repo)
├── svelters-pack.toml             manifest (below)
├── metadata/
│   ├── gtk/*.json                 svelters-element-kind/v0, generated by ingestion with --namespace Adw
│   ├── overrides/gtk/*.yaml       hand annotations (child slots, sync signals, ownership), provenance per fact
│   ├── verified/gtk.json          the pack's verified-facts ledger
│   ├── style/gtk.yaml             ST1-format fragment: setter props for pack kinds, class vocabulary, tokens
│   └── docs/gtk/                  docs ingestion output
├── js/                            npm package root: helpers (toast()), generated types/adw.d.ts, docs pack, tables blob
├── fixtures/gallery-adw/          gallery pages + screenshot tests
└── native/                        optional crate (code packs): build.rs uses the toolkit's build crate with the pack config
```

```toml
# svelters-pack.toml
[pack]
name = "adw"
toolkit = "gtk"
version = "0.1.0"               # pack version; follows svelters lockstep for first-party packs
tag-prefix = "ad-"              # required for every non-core pack
native-prefix = "Adw"           # stripped before kebab-casing: AdwHeaderBar -> ad-header-bar
kind = "data"                   # data | code

[library]
gir = "Adw-1"                   # gtk: typelib namespace-version; qt: pkg-config/cmake name; winui: dlls; apple: frameworks
min = "1.4"                     # oldest library version the metadata is verified against
built-against = "1.9.0"

[init]
call = ["adw_init"]             # data packs: GI functions called once after toolkit init
style-scheme = "Adw.StyleManager:color-scheme"   # takes over SVL_STYLE_SCHEME (section 5)
```

### 2.2 Tags

- **The rule.** A pack tag is `tag-prefix + kebab(native name − native-prefix)`, using the same kebab function N1 uses for core tags.
  - Examples: `AdwHeaderBar` → `ad-header-bar`, `ads::CDockWidget` → `ads-dock-widget` (the namespace and the `C` class prefix both stripped), `CommunityToolkit.WinUI.Controls.SettingsCard` → `ct-settings-card`.
- **The core toolkit has no prefix.** `header-bar` and `ad-header-bar` coexist.
- **Duplicate tags are a load-time error** naming both packs. The generator also checks the prefix against the core tag table, so no core tag may start with a registered prefix.
- **Props, signals and style properties keep native kebab-case names**, as in core. Members inherited from core classes (`GtkWidget` props on an Adw widget) resolve through the core tables (section 3.3).

### 2.3 Opting in

```toml
# app svelters.toml
[packs.adw]                     # npm package @svelters/pack-adw (first-party alias) or any npm name via package = "…"
min = "1.4"                     # optional: raise the floor; typings mark newer kinds as errors
```

- **The CLI wires it in.** `svelters add adw` installs the npm package, writes the `[packs.adw]` table, and adds `@svelters/pack-adw/types` to `tsconfig` `types`.
  - For a code pack it also adds the crate to the app's leaf crate (creating it via `add native` when needed).
  - Registration is **autolinked**: the leaf crate's `build.rs` reads `svelters.toml` and generates `packs.rs` with one `add_pack` call per pack. Nobody hand-edits it.
- **Tags need no import.** They are intrinsic elements. The pack's `.d.ts` augments `svelteHTML.IntrinsicElements` exactly as the core typings do (`packages/renderer/types/index.d.ts`).
- **JS helpers** are ordinary imports: `import { toast } from '@svelters/pack-adw'`.

## 3. Runtime extension

### 3.1 Options considered

| Option | Verdict |
| --- | --- |
| **A. Static only: pack tables compiled into the backend crate** (a cargo feature / extra C++ TU) | Simple, but every pack means a custom runner build, even GIR-described libadwaita. It defeats the prebuilt runners (CLI §3) and turns third-party packs into forks of `svelters-gtk`. Kept as the release-mode linking strategy, not the extension model. |
| **B. Packs as peer backends the host multiplexes** | Fails at the tree boundary. Inserting a core `label` into an `ads-dock-widget`, or an Adw page into a core `stack`, needs the native object behind the other side's handle. Two handle tables would also break identity (X1: one handle per native object) and the cascade rules (M2a). |
| **C. Packs plug into the backend (recommended)** | The core backend keeps the one handle table, liveness tracking, lifetime classes, the loop and style. A pack only maps ids to native operations on native objects (`GObject*`, `QObject*`, `IInspectable*`, `id`). The host sees one backend whose `resolve` knows more names. |
| D. Rely only on toolkit dynamic lookup (GType by name, `objc_getClass`, `QUiLoader`) | It is the engine *inside* C for data packs, but alone it lacks the semantics no runtime carries: child slots, sync signals, ownership, version gates. Those come from the pack's metadata. |

### 3.2 Id layout

```text
bit 31..28  reserved (signal ids carry SVL_LISTEN_* flags in 28..30 already)
bit 27..22  pack index: 0 = core backend, 1..63 = packs in add_pack order
bit 21..0   local id inside the pack (4M); the core's existing ad-hoc ranges
            (GTK extras 0x4001.., typelib methods past METHODS.len(), Qt getters 1<<20..) stay in pack 0
```

Type ids (`describe_type`, `svl_value.type`) use the same split. Well-known types (`SVL_T_*`) stay in pack 0, so a pack can use `SVL_T_RECT` directly.

### 3.3 Routing inside the backend

- **`resolve(SVL_KIND, name)`.** If the name has a registered prefix, the backend asks that pack; otherwise it uses core. The GType, Qt class or GIR name forms resolve the same way.
- **`resolve(member, kind, name)` on a pack kind.** The pack's tables go first, then the core chain of the kind's nearest core ancestor. `AdwHeaderBar` → `GtkWidget` gets `visible`, `css-classes` and so on.
- **`set_prop` / `get_prop` / `call` / `listen` / `describe`** go by the **member id's** pack bits, not the object's kind. A core prop id on a pack object is handled by core; a pack prop id is handled by the pack.
- **`insert` / `remove` / child attributes** go by the **parent's** kind. The parent owns placement, as in X3. A pack child in a core parent uses the core's slot ops, which only need a `GtkWidget`/`QWidget`.
- **`create`** goes by the kind's pack. The pack returns a native object, and the backend mints the handle (`OWNED`, or `TOPLEVEL` per the kind's metadata) and installs its liveness tracking: qdata/`GWeakRef`, `QPointer` + `destroyed`.
- **Borrowed objects a pack hands out** (ADS dock areas, floating containers; `AdwTabPage` from `get_page`) go through `services->handle_for(native, kind, SVL_LIFE_BORROWED)`. Identity, weak refs and the death cascade follow the X1 rules unchanged, because they live in one place.
- **Events.** A pack's listen connects natively and reports with `services->post_event(h, full_signal_id | flags<<28, …)`. Sync handlers use `services->call_sync`, which is the host's `call_sync` passed through. Callbacks use `services->invoke_callback`/`release_callback`. So `call_sync`, `SVL_SYNC_BUSY`, callback scopes and async work across the boundary with no new semantics.

### 3.4 Data packs need no `svl_pack_ops`

- **The pack's tables blob holds everything a reflective backend needs:**
  - kinds, props, signals, slots, attrs and types;
  - slot ops expressed declaratively: a property set, a named method call, or `custom`, which forces a code pack;
  - handler results, `since`, and lifetime class.
- **The blob is the JSON the generators already produce (the `facts` shape)**, so a runtime table loader in each backend replaces the compiled `KINDS`/`PROPS` arrays for pack ids.
- **Per toolkit:**
  - **GTK:** load the typelib and call the `init` functions through GI. Slot ops become GI method calls (X1 already passes object arguments). This needs a generic slot-op interpreter next to the generated typed `slots.rs`.
  - **Qt:** a data pack is possible only for libraries with a designer plugin (`QUiLoader` factory), with members through the QMetaObject engine (section 4.2).
  - **WinUI:** pack dlls + `IXamlMetadataProvider` (WIN1's dev path).
  - **Apple:** framework load + ObjC runtime (MAC1's dev path).

## 4. ABI changes (draft)

### 4.1 `svl_backend` v2.5 (additive, may be NULL)

```c
/* ABI v2.5 (custom widgets). Register a pack before `run`. Returns the pack index (1..63) or < 0
   with last_error (toolkit mismatch, duplicate prefix/tag, library too old, init failed). Packs
   stay registered for the backend's lifetime (hot reload keeps them). */
int (*add_pack)(void *self, const struct svl_pack *pack);
```

The host reads `[packs]` from `svelters.toml`. Data packs it builds as an `svl_pack` with `ops == NULL` from the manifest and blob; code packs it gets from the leaf crate's generated registration, or later from `dlopen` + `svl_pack_entry`. It calls `add_pack` for each one before `run`. Nothing else in the host changes, because names, ids and events are already opaque to it.

### 4.2 New header `svelters_pack.h` (backend ↔ pack; pack ABI 1)

```c
#define SVL_PACK_ABI_VERSION 1u
#define SVL_ID_PACK_SHIFT 22
#define SVL_ID_PACK_MASK  0x0FC00000u
#define SVL_ID_LOCAL_MASK 0x003FFFFFu

typedef enum svl_toolkit { SVL_TK_GTK = 1, SVL_TK_QT = 2, SVL_TK_WINUI = 3, SVL_TK_APPKIT = 4, SVL_TK_UIKIT = 5 } svl_toolkit;

/* Implemented by the core backend, handed to the pack in init. `native` is GObject* / QObject* /
   IInspectable* / id, per toolkit. All calls main-thread only. */
typedef struct svl_pack_services {
  uint32_t abi;  /* SVL_PACK_ABI_VERSION */
  void *self;
  uint32_t pack_index;                                   /* this pack's index, for building full ids */
  svl_handle (*handle_for)(void *self, void *native, svl_id kind, uint32_t lifetime /* svl_lifetime */);
  void *(*native_of)(void *self, svl_handle h);         /* NULL for stale/foreign handles */
  void (*post_event)(void *self, svl_handle h, svl_id signal, const svl_value *args, size_t n);
  int (*call_sync)(void *self, svl_handle h, svl_id signal, const svl_value *args, size_t n, svl_value *out);
  int (*invoke_callback)(void *self, uint64_t cb, const svl_value *args, size_t n, svl_value *out);
  void (*release_callback)(void *self, uint64_t cb);
  void (*report_destroyed)(void *self, svl_handle h, uint32_t reason /* svl_gone */);
  /* The core's value conversions, so packs don't re-implement serdes. `native_value` is GValue* (GTK),
     QVariant* (Qt), IInspectable** (WinUI), id* (Apple). */
  int (*to_native)(void *self, const svl_value *v, const svl_slot_desc *as, void *native_value);
  int (*from_native)(void *self, const void *native_value, svl_value *out);
  svl_id (*core_resolve)(void *self, uint32_t what, svl_id kind, const char *name, size_t len);
} svl_pack_services;

/* Every member may be NULL: the backend then uses its reflective engine with the pack's tables.
   Ids passed in and out are LOCAL ids (the backend adds/strips the pack bits). Returns 0 / >= 0 on
   success, < 0 with last_error. */
typedef struct svl_pack_ops {
  int (*init)(void *self, const svl_pack_services *svc);
  void (*shutdown)(void *self);
  svl_id (*resolve)(void *self, uint32_t what, svl_id kind, const char *name, size_t len);
  void *(*create)(void *self, svl_id kind);             /* new native object; GTK: floating refs are sunk by the backend */
  int (*insert)(void *self, void *parent, void *child, void *before, svl_id slot);
  int (*remove)(void *self, void *parent, void *child);
  int (*set_prop)(void *self, void *obj, svl_id prop, const svl_value *v);
  int (*get_prop)(void *self, void *obj, svl_id prop, svl_value *out);
  int (*call)(void *self, void *obj, svl_handle h, svl_id method, const svl_value *args, size_t n, svl_value *out);
  int (*listen)(void *self, void *obj, svl_handle h, svl_id signal, bool on, uint32_t flags /* SVL_LISTEN_* */);
  int (*set_child_attr)(void *self, void *parent, void *child, svl_id attr, const svl_value *v);
  int (*get_child_attr)(void *self, void *parent, void *child, svl_id attr, svl_value *out);
  const svl_member_desc *(*describe)(void *self, uint32_t what, svl_id kind, svl_id member);
  const svl_type_desc *(*describe_type)(void *self, svl_id type);
  /* Style hook: return 1 = handled (core skips its own handling), 0 = not mine, < 0 = error.
     Used for SVL_STYLE_SCHEME takeover (libadwaita) and pack sheets (ADS). */
  int (*style)(void *self, uint32_t op, svl_handle h, const svl_value *v);
  const char *(*last_error)(void *self);
} svl_pack_ops;

typedef struct svl_pack {
  uint32_t abi;                /* SVL_PACK_ABI_VERSION */
  uint32_t toolkit;            /* svl_toolkit; add_pack refuses a mismatch */
  const char *name;            /* "adw" */
  const char *version;         /* pack version */
  const char *tag_prefix;      /* "ad-" */
  const char *const *libraries;/* toolkit-specific loads, NULL-terminated: "Adw-1" typelib, dll names, frameworks */
  const char *tables;          /* generated tables blob (UTF-8 JSON, svelters-pack-tables/v1) */
  size_t tables_len;
  void *self;
  const svl_pack_ops *ops;     /* NULL for data packs */
} svl_pack;

/* Exported by dlopen-able code packs (phase 4). Returns NULL when `host_pack_abi` is unsupported. */
typedef const svl_pack *(*svl_pack_entry_fn)(uint32_t host_pack_abi);
#define SVL_PACK_ENTRY_SYMBOL "svl_pack_entry"
```

Why a separate header: the backend↔pack interface passes native pointers. That is fine *below* the host but must never reach JS (PLAN rule 4), and keeping it out of `svelters_backend.h` makes that structural. The value model (`svl_value`, descriptors) is shared by including `svelters_backend.h`.

## 5. Styling hooks (ST1 format)

A pack ships `metadata/style/<tk>.yaml` in the ST1 table format. The style generator merges core + pack fragments, and a property defined twice for the same kind is an error.

- **Setter properties for pack kinds.**
  - Examples: `ad-clamp { maximum-size: 600 }` (setter `maximum-size`) and `ad-wrap-box { child-spacing }`.
  - `ads-dock-widget` gets `minimum-size-hint-mode` and similar.
  - The generator checks every target against the pack's verified metadata, as ST1 does for core.
- **CSS selectors.**
  - GTK CSS node names for pack widgets (`headerbar` inside `AdwHeaderBar`, `toolbarview`, `navigation-view`) come from the pack's docs ingestion.
  - QSS type selectors for namespaced Qt classes use `ads--CDockWidgetTab`.
  - The docs matrix lists both.
- **Class vocabulary (documentation only).** It covers Adwaita style classes (`card`, `boxed-list`, `navigation-sidebar`, `toolbar`, `pill`, `flat`, `suggested-action`, `title-1`…). `svelters docs ad-…` and the editor completion show them.
- **Tokens.** A `tokens:` map binds `--sv-*` to the library's variables: `--sv-accent: var(--accent-bg-color)` (Adw ≥ 1.6), with `@accent_bg_color` below that.
- **Op takeover through `ops->style` or the manifest's `style-scheme`.**
  - libadwaita must own `SVL_STYLE_SCHEME`. Setting `AdwStyleManager:color-scheme` replaces our `gtk-application-prefer-dark-theme` write, which libadwaita reports as unsupported.
  - The per-provider `prefers-color-scheme` handling stays in core.
  - ADS can append its default QSS into the X6 sheet chain instead of setting a widget-level sheet that would beat the app's `<style>`.

## 6. Dev mode and release

| Toolkit | Dev (prebuilt runner, no cargo per edit) | Release (M6) |
| --- | --- | --- |
| GTK | data packs: typelib + tables + GI invocation; app Rust widgets need the leaf crate (registration) | the M6 binding linker covers pack roots with the same generator, pointed at the pack's metadata; symbols newer than `min` go through `dlsym`/GI, never hard links |
| Qt | **new: a QMetaObject reflective engine in the Qt backend** (props via `QMetaProperty`, signals via a generic `qt_metacall` receiver, slots/invokables via `QMetaMethod::invoke`). It covers app `Q_OBJECT` widgets given a factory, and designer-plugin libraries with none. Code packs (ADS) are compiled once when the pack is added (leaf crate), never per `.svelte` edit | `svelters-qt-build` generates core + pack C++ in the leaf crate; `Config::pack(path)` adds the pack's metadata, sources, include dirs and link libs |
| WinUI | pack dll + its `IXamlMetadataProvider`; events through the universal delegate when WIN1 has it, generated connectors before that | windows-bindgen over the pack winmd, statically typed calls |
| AppKit/UIKit | ObjC runtime (macOS: dynamic frameworks may be loaded at runtime; iOS: linked) | typed `objc_msgSend` for roots; pack frameworks linked |

What works with no codegen at all:
- any GObject type that is registered, or reachable through a typelib;
- any ObjC class that is linked, or an `@objc` Swift class;
- any WinUI type whose library ships an `IXamlMetadataProvider` (properties; events are pending WIN1);
- on Qt, only after the new engine lands, and then only for `Q_PROPERTY`/signals/slots/`Q_INVOKABLE` plus a factory.

Plain C++ methods (most of ADS) always need generated thunks.

## 7. Metadata ingestion for libraries without official docs metadata

| Source | Use | Tool |
| --- | --- | --- |
| GIR | GObject libraries (Adw, app Vala/C libs) | `tools/metadata/gtk/ingest.py --namespace Adw --gir Adw-1` (parameterise the ~10 hardcoded `"Gtk"`) |
| GObject runtime introspection | Rust GObject subclasses (no GIR) | new: a small `svelters-gtk` dump mode (`--dump-types MyAppGauge`) that writes v0 JSON from `GParamSpec`/`g_signal_query`, so it runs the app's real registration code |
| `moc --output-json` | Qt `Q_OBJECT` classes: props, signals, slots, invokables, enums (if `Q_ENUM`'d), class info | new `tools/metadata/qt/ingest_moc.py` (probe: `cw_moc_json.py`) |
| libclang | Qt plain public methods, constructors, enums without `Q_ENUM`, default args | same tool; the libclang setup is shared with the Apple probe (`apple_objc_dump.py`) |
| `.sip` / PySide typesystem | ownership (`/Transfer/`, `/TransferThis/`, `/TransferBack/`) when a library ships Python bindings | `origin: sip` facts in the same ingestion |
| winmd | WinUI component libraries | WIN1's `winmd_dump` with the pack winmd + dependency winmds |
| ObjC headers / `Module-Swift.h` | ObjC and `@objc` Swift | MAC1's libclang pass; `-Swift.h` is the exact runtime-reachable Swift surface |
| `.swiftinterface` / `swift-api-digester` | report Swift members that need `@objc` | diagnostics only |

- **Overrides, the ledger and docs live in the pack** (`packs/<name>/metadata/…`).
- **The generators take a list of metadata roots:** core first, then each pack. A pack override may annotate only the pack's own kinds. The fact "an Adw widget is accepted in a core `stack`" is a property of the core slot's `accepts: [Gtk.Widget]`, so it needs no cross-pack edits.
- **The A1 agent loop runs per pack unchanged.** Draft annotations, generate verification tests, run them headless, and merge only passing facts.

## 8. CLI integration (extends `plans/research/CLI.md`)

- **`svelters add <pack>`.** It installs, edits `svelters.toml`/`tsconfig`, and autolinks code packs into the leaf crate.
  - For a code pack and a prebuilt runner, it prints that a source build of the runner is now needed and why. It does that once, at add time.
  - Later it can fetch a prebuilt pack binary instead (`@svelters/pack-ads-<os>-<arch>`, dlopen).
  - It is idempotent and takes `--json`.
- **`svelters docs`.** It loads the docs pack of every pack in `[packs]` next to the core pack. `svelters docs ad-header-bar` works, and `svelters docs --packs` lists the packs with their prefixes and library versions. Pack docs are built from the pack's docs IR, the same way the core docs are.
- **`svelters doctor`.** It checks each pack's library: `pkg-config --atleast-version=1.4 libadwaita-1`, ADS found/vendored, WinUI dlls present.
- **`svelters gallery <tk> --pack adw`.** It runs the pack's gallery.
- **`svelters pack new <name> --toolkit qt --from-headers …`** (later). It scaffolds a third-party pack and runs ingestion.

## 10. Phasing

| Phase | Content | Proves |

CW1 is a single lane. It touches `svelters-gtk` (runtime tables, slot interpreter, `add_pack`), the ABI header (v2.5 member + `svelters_pack.h`, with no ops consumers yet), tools (namespace, roots) and the host (`[packs]` loading). Rough size: comparable to X4 or X7.

## 11. Open questions

1. **Prefix governance.**
   - Are prefixes first-come in a registry kept in the CLI (`ad-`, `ads-`, `ct-`)?
   - May an app re-prefix a pack in `svelters.toml` to resolve a clash?
2. **Breakpoints.** Is the one-frame lag of JS-driven `apply` acceptable as the default? Or should `ad-breakpoint-setter` (native, flicker-free) be the documented primary path? This needs a probe of `call_sync` inside size allocation.
3. **GTK slot ops.** Should the core also move from typed generated `slots.rs` to the generic interpreter CW1 builds, giving one path? Or does core stay typed for speed and release parity?
4. **ADS licensing and release builds.** Shared-library-only for ADS, or allow static linking for GPL/LGPL-compatible apps behind a flag?
5. **Windows Community Toolkit.** Is a .NET runtime dependency acceptable for a pack, or do we support only native WinRT component libraries?
6. **Prebuilt code-pack binaries (CW5).** The matrix is OS × arch × Qt minor. Is it worth it, or is "code packs need a source-built runner" an acceptable rule?
7. **Pack/core compatibility.** A pack's tables carry `schema` and the core metadata version it was generated against. Should `add_pack` refuse on a schema mismatch, or warn?
8. **Tables blob format.** Is JSON parsed at startup fine (Adw is ~100 kinds), or do we want a generated binary format before M6?
9. **Rust GTK widgets: methods.** Their methods are not in any typelib. Do we generate GI-free thunks from `#[svelters::export]` attributes in the app crate, or limit them to props and signals?
